# Supply chain graph

Use this skill when a user wants a portfolio-wide software supply chain view or a dashboard that explains which projects depend on a package or repository and why an alert matters.

## Work from evidence

For JavaScript, keep three evidence layers distinct: manifest declarations, literal imports found in source files (including browser import map URLs), and versions resolved by a supported lockfile. A source import shows observed use but does not prove an installed npm package or a security check. Show local module edges and external import edges in a separate Source imports lens; report unscanned files and unknown resolution explicitly.

1. Start with project folders the user supplies. If they want discovery, ask them to choose specific parent folders; never start a whole-computer search. The CLI can `init` a private config, `set-root` for known folders, and `discover` under selected parents. Review discovery candidates before adding them: a workspace package or duplicate checkout is not automatically a separate product. Keep personal paths, tokens, private repository names, and raw local snapshots outside the public skill repository. Use the local `serve` mode when the user needs to set a root from the dashboard; a saved HTML snapshot cannot write to the portfolio config. In that mode **Choose project folder** opens a native folder dialog through the local server and fills the Set root form, and the user still has to click **Add and scan** before anything is saved; **Discover projects under a parent folder** runs the same bounded discovery from the dashboard and lists candidates for review before anything is adopted. The empty inspector panel is the start-here guide, so point a new user there first.
2. Read manifests and lockfiles together. Treat the manifest as intent and the lockfile or build artifact as resolved state. Distinguish no root JavaScript manifest from an unreadable file, and show nested manifests that were discovered but not scanned. Label unsupported, missing, stale, and inaccessible sources as coverage gaps. Never report “no vulnerabilities” from a local inventory alone.
3. Model **project → declared JavaScript request → resolved occurrence → versioned artifact** when a manifest and lockfile are available. Keep occurrence paths and edge evidence so the same artifact can be shared across projects without inventing a false transitive route. Git repositories, actions, containers, and package registries are distinct source types.
4. For every finding, retain its source, observed timestamp, affected version or commit, impacted projects, and at least one dependency path. Separate security advisory, npm deprecation, newer `latest` tag, mutable reference, remote drift, and coverage gap. A new release alone is informational unless the user's policy says otherwise. Record attempted, checked, failed, and unqueried states separately; do not turn a failed lookup into a clean result. The CLI's `evaluate` command applies a versioned policy deterministically and writes a policy result with stable finding identities and these coverage states; validate documents with `validate --schema`. An OSV fixed boundary or newer npm `latest` tag is a remediation lead, not proof that an update fixes every advisory; show source severity only when supplied.
5. Make a connected node/edge network the primary view. Provide separate lenses for JavaScript manifest requests, literal source imports, resolved npm/pnpm dependencies, and GitHub source relationships. Bubble critical, advisory, deprecation, newer-latest, unknown-check, and coverage-gap filters above the graph; connect marked nodes to source evidence and a suggested next step in the inspector. Offer a complete direct-link view across projects as well as a bounded multi-step path view. In a bounded portfolio sample, distribute visible paths across projects so the first large project does not dominate. Label graph columns, fit width for tall graphs, and provide zoom plus scrolling. Let the user choose a project or the portfolio, page through every configured project or show all in a scrollable direct chart, search dependency paths, inspect nodes and edges for path, version, scope, and source, and clear selection by clicking blank graph space. State clearly when a dense graph is showing bounded paths and how many relationships are omitted; keep full relationships in an accessible index and exportable JSON. A local-only folder action may open a selected node's verified project directory. Show a version timeline and alert queue when those data sources exist.
6. Hand a model only the redacted packet from `packet`, never a raw snapshot. Require a `proposal` document and run `check-proposal` against the packet; a proposal that cites anything the packet does not contain is rejected. A human records a `decision` bound to the proposal hash and source commit, checked with `check-decision`, before any separate job writes code or opens a pull request; read `references/hitl-remediation.md`. Diff against the last accepted snapshot for notifications. Deduplicate by finding identity and affected artifact, preserve acknowledgement and suppression state outside generated snapshots, and send externally only with the user's authorization and configured channel.

The bundled [local starter](README.md) can discover local roots and scan npm lockfile v2/v3, pnpm v9 snapshots, root JavaScript declarations, bounded literal source imports and root HTML import maps, GitHub Actions uses, Python requirements, Git submodules, and cached Git metadata. Its opt-in enrichment checks OSV and public npm metadata; a separate OSV detail lookup adds summaries, severity where supplied, and fixed boundaries. The local editing server can save a root, rescan without advisory lookups, and keep basic action status and notes in a private file. Its dashboard and diff output demonstrate the data contract; they are not a complete security scanner, remediation tracker, or notification delivery service. Read [architecture and coverage](references/architecture.md) before extending adapters, remote enrichment, or alert policy.

For public packaging and private-data boundaries, read [security and privacy](SECURITY.md). For CI or LLM handoffs, read [pipeline integration](references/pipeline-integration.md); keep deterministic policy and authorization outside the model.
