# Pipeline and LLM integration

## Current machine output

The CLI emits JSON snapshots with source coverage, nodes, edges, findings, and optional enrichment. The diff command compares two accepted snapshots and writes schemaVersion 1, timestamps, and candidate events. It does not persist alert ownership, apply a release gate, deliver notifications, open issues or pull requests, or validate a proposed fix. Keep all real output in private storage outside the public skill repository.

The init command creates an empty versioned config and refuses to replace an existing file. For command-line composition, use --out - to write data to stdout; diagnostics and scan progress go to stderr. Do not stream private data into public CI logs. Discovery requires explicit --search-root arguments, can be bounded with --depth and --max-directories, and will reject a whole drive or filesystem root. Its report has incomplete, truncated, and unreadableDirectories fields; policy should treat incomplete discovery as a coverage gap. The API in scripts/discover.mjs can be called by a local wrapper when a pipeline already has an approved project registry.

For a selected repository or private portfolio runner:

1. Run scan with a private config and output path. Record the source commit, scan time, parser status, and coverage. A CI checkout of one repository is only evidence for that checkout; a portfolio run needs explicit access to each selected root.
2. Where the data-sharing policy allows it, run enrich and then advisory-details on the private snapshot. Never interpret a failed or unqueried advisory source as zero advisories.
3. Run diff against the last accepted snapshot and write events to a private path. Compare against the last accepted snapshot, not merely the last attempted run. Store the accepted baseline, event IDs, acknowledgements, and delivery receipts privately.
4. Apply a deterministic policy to coverage and evidence before sending work to an LLM. For example, require a successfully checked advisory source for a vulnerability claim, and route missing lockfiles or failed lookups to a coverage queue. Use impacted dependency paths, not a package name alone, to locate owners.
5. Build a small, reviewed context packet for each actionable event: event and finding IDs, affected project alias, resolved artifact or commit, one path of typed edges with source file evidence, advisory source and checked time, coverage state, and relevant policy rule. Omit local roots, credentials, unrelated nodes, and private repository labels unless the model service and data policy explicitly allow them.
6. Ask the LLM for a structured **proposal** with eventId, summary, evidenceIds, suggestedAction, validationSteps, unknowns, and confidence. Validate IDs against the snapshot; reject fabricated paths or sources. Treat all package metadata, advisory text, and repository content as untrusted quoted data. The model cannot change the policy result or mark a finding resolved.
7. Route a proposal to a human reviewer or a separately authorized tool. A pull request, issue, notification, or code change needs its own credentials, narrow permissions, validation, and approval rule. Re-scan after any change to determine whether the finding is still observed.

The graph and event JSON are useful inputs to an agent that answers “which projects are affected?” or drafts a remediation plan. Do not hand a model a complete private snapshot by default. For hosted models, check the organization's data handling requirements before sending even a redacted packet.

## CI placement

Run per-repository collection on a private runner or in that repository's CI with read-only checkout permissions. Keep real JSON and HTML out of public workflow artifacts, logs, and Pages builds. A portfolio aggregator can receive approved per-repository packets and update a private dashboard. Keep the public skill's own CI limited to its synthetic fixtures and tests. If using GitHub Actions, declare minimal GITHUB_TOKEN permissions for each job; a later issue or pull-request job should be isolated from the read-only scan job. `examples/ci/scan.yml` and `ci-setup.md` are the copyable starting point: pinned actions, a pinned skill commit, read-only token, private `$RUNNER_TEMP` output, an aggregate-only job summary via `summary --result FILE --out -`, opt-in enrichment on dispatch only, and distinct exit codes for tool failure (1) and a configured gate (3).

## Contracts and deterministic policy

The documents above now have versioned JSON Schemas under `contracts/` (snapshot v1, diff events v1, policy v1, policy result v1), checked by `validate --schema NAME --file FILE`. `evaluate --snapshot FILE --policy FILE --out FILE [--at ISO-TIME] [--previous RESULT]` applies a versioned policy deterministically: the same accepted snapshot, policy, and evaluation time always produce the same result, and the evaluation time is an input so freshness tests are repeatable. The result records scan identity and source commits, freshness, a coverage state for every npm package version and check (`checked-and-none`, `checked-with-results`, `failed`, `unqueried`, `unsupported`, `stale`), findings with stable identities derived from rule, advisory, ecosystem, exact artifact or commit, project, and occurrence (never absolute paths or timestamps), a mapping back to the scanner's v1 finding IDs, and a gate verdict. A policy may route coverage gaps to `needs-review`; it has no way to label anything `safe` or `resolved`. With `--previous`, a finding becomes `no-longer-observed` only after a comparable successful check; a failed or skipped later lookup leaves it `unknown`. Event identities include the transition and observed version so retries deduplicate while a reappearance alerts again. The default policy reports and fails nothing; a configured `gate.failOn` makes the command exit 3, distinct from exit 1 for invalid input. See `contracts/README.md`.

## Event packets and user-owned delivery

`packet --result FILE --out FILE [--policy FILE] [--include LIST] [--transitions LIST]` builds the redacted event packet (`contracts/agent-packet.v1.schema.json`) from an accepted policy result: per item a stable event and finding ID, the transition, the project ID or the opaque alias from the policy's `aliases`, the artifact or commit, one typed dependency path, evidence entries with citable `ev_` IDs, the files a remediation may touch, the coverage state and rule, and a packet-level content hash. It contains no absolute roots, source text, credentials, unrelated nodes, or private remote labels. The packet is data; nothing in the scanner delivers it. `examples/notify/webhook.mjs` is a separate, disabled-by-default consumer: HMAC-signed bodies, an idempotency key per event, a timeout and bounded retries, private delivery receipts, a private suppression and acknowledgement file with owner, reason, and expiry, and no delivery of `unknown` transitions as alerts. Acknowledgement never resolves anything.

## Proposals and human decisions

`contracts/proposal.v1.schema.json` and `contracts/decision.v1.schema.json` are the remediation contract; `hitl-remediation.md` is the guide. `check-proposal --proposal FILE --packet FILE` rejects a proposal that cites an evidence ID, file, artifact, advisory ID, dependency path, or commit the packet does not contain, proposes a change for an event the policy did not mark actionable, or was written against another packet hash. `check-decision --decision FILE --proposal FILE --packet FILE` exits 0 only for an unexpired approval bound to the exact proposal hash, packet hash, and source commit, and warns when the recorded method is a manual note rather than a pull request review or protected environment. No model is called by default; no job in this repository writes code, issues, or pull requests.

## What still needs implementation

Ownership mapping from dependency paths to teams, a `workflow_call` wrapper once the example workflow interface is stable, and adapters for further ecosystems. Ecosystem collectors should be separate adapters with explicit supported formats, provenance, coverage states, and fixtures; notifier and remediation adapters should be separate from collection. SBOM import/export and SARIF output are reasonable future connectors after the graph identity and finding mapping are stable. A safe first integration is read-only: generate a private summary and proposed actions, then review them.
